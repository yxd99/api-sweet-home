# api-hardening — make the API stable, tested, secure and MVP-ready
Branch: `feat/api-hardening` (from `main` @ `a7c6305`). Delivery: work-unit commits on this branch; push/PR/merge stay the user's decision. Test runner: jest (`pnpm test` for unit, `pnpm test:e2e` for e2e after T1).

## Specs
S1. The user asked: "Necesito que quede estable y cubierto todo, deja todo en automatico para poder trabajar sin problemas sin esperar que yo apruebe cosas, dejalo bien, con seguridad obviamente, agrega pruebas, etc, revisa huecos, deja la api funcionando excelente, el MVP no solo sera la API sino también una web". Interpretation: autonomous implementation, no approval round-trips, security by default, real test coverage, close every hole found, and the MVP eventually includes a web client.
S2. Every endpoint must answer with a correct HTTP status: never a 500 for missing, empty or malformed input; 400/401/403/404 instead. Evidence: `POST /api/auth/refresh-token` and `POST /api/auth/disable-tokens` with no header return 500 today (`src/api/auth/auth.controller.ts:24,29` read raw headers with no validation; TypeORM 1.x throws on an undefined `where` value).
S3. Authentication must be brute-force resistant: the OTP is a single-use, cryptographically random code, rate limited, and invalidated after a successful login. Evidence: `src/common/utils/generate-code.ts:6` uses `Math.random()` for a 4-digit code (10k combinations), `auth.service.ts:55` accepts it until the 15-minute expiry and never clears it, and no endpoint has a throttle.
S4. Authorization must be enforced server-side on every read and write: a user may only reach households they belong to. Evidence: `src/api/homes/homes.service.ts:52` `findOne(id)` is unscoped, so `GET /homes/:id` leaks any household and its members' emails; `homes.service.ts:76` lets any member delete the household.
S5. Configuration must fail fast: the process refuses to boot when a required variable is missing or too weak, and `.env.example` documents every variable. Evidence: the app booted with no `JWT_ACCESS_TOKEN_EXPIRY` and only failed at the first `sign()`; `ENV` is unset, and `typeOrm.ts:7,20` decides `synchronize` from `environment !== 'prod'` so `ENV=production` would leave schema auto-sync on; there is no tracked `.env.example`.
S6. Test coverage must be real and runnable: unit tests for pure logic, and end-to-end tests that exercise the real HTTP surface against a real database, with mail delivery stubbed. Evidence: the only test is `src/shared/mail/mail.service.spec.ts` and `test/app.e2e-spec.ts` cannot resolve `@api/auth/auth.module` (`test/jest-e2e.json` has no path mapping) and asserts a `/` route that does not exist.
S7. Operational basics for a service that will run elsewhere: security headers, a restricted CORS origin list, a global exception filter that never leaks internals, a health endpoint, graceful shutdown, and a container/build path. Evidence: `main.ts` sets `cors: true` (any origin), has no helmet, no exception filter, no health route and no `enableShutdownHooks`; the repo has no Dockerfile and no CI.
S8. Fix real functional bugs found while mapping, in addition to hardening. Confirmed: `src/api/household_members/household_members.service.ts:55-58` overwrites `user` with the host before the `user === null` check, so inviting a new email never creates the user and the member insert fails with an FK error; `GET /personal-markets` and `GET /products` read `homeId` from the body (`@Body() { homeId }: FindAllDto`) so a bodiless GET is a 500.
S9. Public behaviour changes must be reported, not slipped in. The E3 notes already carry two: `refresh-token` with no header 201 -> 500, and `disable-tokens` with no header 201 -> 500. Their fix must be described in the commit body and in this log.
S10. The web client is a separate deliverable. It is not built from this repository; it starts only after the API items above are green, and its stack and repository are a product decision to be taken with the user at that point.
S12. A revoked token must stop working. `POST /api/auth/disable-tokens` only flips `auth.isEnable` in storage, while `AuthGuard` checks nothing but the JWT signature (`auth.guard.ts:31-41`), so the disabled access token keeps working until it expires. The e2e suite covers the current storage behaviour only; the desired behaviour becomes a covering test when T3 lands.
S11. Nothing may be pushed, merged, or opened as a PR without the user; no commit attribution to AI; conventional commit messages.
